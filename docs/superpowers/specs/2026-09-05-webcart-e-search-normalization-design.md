# WebカートE案 検索表記ゆれ対応 設計

## 対象

- 最新版E案: `09-sakura-staging/category-comparison/e-horizontal-product-list.html`
- 表示・検索処理: `09-sakura-staging/category-comparison/comparison.js`
- 商品データ生成: `09-sakura-staging/scripts/build_snapshot.py`
- 本番Webカート、NILE、商品CSV、本番DBは対象外

## 現在の確認結果

- E案の検索は、入力値を前後トリムして小文字化し、商品コード・商品名・規格へ部分一致している。
- E案では、NFKC正規化、ひらがな・カタカナ統一、漢字の読み検索、カテゴリー名検索を行っていない。
- 購入フロー側にはNFKC正規化があるが、漢字の読み検索とカテゴリー名検索はない。
- 商品スナップショットは `build_snapshot.py` が生成するため、検索用データも同じ生成時点で作れる。
- 菜の花村公式ホームへの既存リンクは、E案のPC・スマホメニューと購入フローで既に別タブ指定になっている。
- 現在のPython環境には日本語読み変換ライブラリが入っていない。

## 採用設計

1. 読み変換はブラウザやPHP 5.3で毎回行わず、スナップショット生成時に行う。
2. SudachiPyと固定版の辞書をローカル生成環境だけで使い、商品名とカテゴリー名を形態素へ分けて読みを生成する。
3. 公開側は生成済みの軽量な `search-index.json` を読むだけにする。
4. 正規化はNFKC、小文字化、空白除去、カタカナからひらがなへの統一を共通処理にする。
5. 商品ごとに、商品コード、商品名表記、商品名の読み、元カテゴリー名、その読みを検索対象にする。
6. 語ごとの漢字表記と読みの対応も自動生成し、「人参」入力を「にんじん」へ展開できるようにする。
7. 自動生成で扱えない別名だけを、小さな補助辞書へ登録できるようにする。全商品を手作業登録しない。
8. 未知語、読み未取得、同じ表記に複数の読みが生成された語を、公開対象外の確認一覧へ出す。
9. 検索索引と商品カタログの `snapshot_id` が一致しない場合は、現在の表記検索へ安全に戻す。
10. 現在のカテゴリー選択範囲、商品並び順、表示名、購入フローは変更しない。

## 検索例

- `人参` → 自動生成した語彙対応で `人参` と `にんじん` の両方を検索
- `にんじん` / `ニンジン` → ひらがなへ統一し、商品名表記と読みの両方を検索
- `ゆうき` → `有機` を含む商品名の自動生成読みへ部分一致
- `９０１１５` → NFKCで `90115` に統一して商品コード検索
- `千葉 土付` → 空白を除去して `千葉土付` として検索

## 読みの確認対象

自動変換の正誤を完全に機械判定することはできない。そのため、次を確認候補として自動出力する。

- Sudachiが未知語と判定した語
- 読みが空、または漢字が残った語
- 同じ表記から複数の読みが生成された語
- 補助辞書で読みを上書きした語

確認済みの修正は語単位の補助辞書へ追加し、次回生成から全該当商品へ反映する。

## 公開・本番境界

- 今回の実装対象はローカル試作品のみ。
- さくらサーバーへの配置、外部公開、本番Webカートへの移植は別承認。
- NILE、CSV、本番DB、商品表示名は変更しない。
